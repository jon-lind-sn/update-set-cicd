Update Set CI/CD: the developer workflow

What happens from the first code change to a committed update set in production. Continuous integration and delivery (CI/CD) runs in GitHub Actions, so the developer writes code, merges a pull request, and starts the production promotion.

Developer GitHub Actions (automatic) ServiceNow instance Human approval
  1. 1

    Write the change

    Developer, on a feature branch

    Edit the Fluent app (tables, business rules, fix scripts) in code. Build and try it on a personal dev instance if desired.

    now-sdk buildnow-sdk install
  2. 2

    Open a pull request (PR)

    Developer

    Push the branch and open a PR into main. This starts the automatic checks.

  3. 3

    Checks run on the PR

    GitHub Actions, no instance changes

    The app is built and packaged into an update set file to prove it is valid. Nothing touches any instance yet.

    npm cinow-sdk buildupdate-set-cicd generate
    Result: green check or red X on the PR, with the update set XML attached as a download.
  4. 4

    Review and merge

    Developer and reviewer

    A teammate reviews the code and the green checks, then merges the PR into main.

  5. 5

    Generate the release update set

    GitHub Actions, on merge to main

    The build runs on the merged code and generate creates the update set from it. This is where the update set is born: no instance has it yet, and git holds the source of truth. The file is built once.

    now-sdk buildupdate-set-cicd generate
  6. 6

    Deploy to TEST

    GitHub Actions to the TEST instance

    The generated file is imported to TEST: uploaded, previewed, and committed. The run summary prints the update set name. If the preview finds a problem (for example a conflicting newer change), the run stops here and nothing is committed.

    update-set-cicd import
    Result: the change is live on TEST for testing.
  7. 7

    Start the PROD promotion and approve it

    Human, in GitHub

    When the version is ready, start Sample app: promote to PROD by hand with the update set name. The PROD environment requires a named reviewer, and the job pauses until they click Approve. Merges are never blocked while it waits.

  8. 8

    Move to PROD

    GitHub Actions to the PROD instance

    The update set TEST committed is copied to production, previewed, and committed, the same as a manual pull from TEST.

    update-set-cicd move
    Result: the change is live. The run log records who approved and what was committed.

If something fails

  1. Failure in step 3: the PR shows a red X. Fix the code, push again, and the checks re-run.
  2. Failure in step 6 (TEST preview problem): the run stops, nothing is committed, and the log lists each problem with a link to the retrieved update set on the instance.
  3. Rejection in step 7: nothing reaches production.

TEST receives the update set by import because nothing earlier holds it. PROD receives it by move from TEST, which creates the same record a manual update set pull from TEST creates. Each merge deploys to TEST only, so a pending PROD approval never blocks later merges.
